# AthleticOS -- Data Handling & Security Brief

For Lisa Wong -- addresses the student data hosting concerns raised April 15, 2026. Short and concrete; happy to expand any section on request.

## What data AthleticOS holds

| Category | Specifics | Source |
|----------|-----------|--------|
| Athletic schedules | Games, practices, recurring events, blockers | Created by coaches/AD in AthleticOS, or read from Blackbaud |
| Teams + facilities | Team names, sport, season, facility names | TCA (manual or Blackbaud sync) |
| Roster | Student name, grade, team membership | Blackbaud sync (read-only) |
| Coach accounts | Name, email, role, hashed password | TCA invites + self-registration |
| Notification logs | What was sent, to whom, when | Auto-generated by app |
| Audit log | Every write, by whom, when | Auto-generated |

**What we explicitly do NOT store:** parent contact info, grades, financial info, medical records, SSNs, addresses, photos, biometric data.

## Where it lives

| Layer | Service | Region | Notes |
|-------|---------|--------|-------|
| App servers | Render (web service) | US-East | SOC 2 Type II certified provider |
| Database | Render Managed PostgreSQL 16 | US-East | Encrypted at rest (AES-256), encrypted in transit (TLS 1.2+), automated daily backups, point-in-time recovery (7 days) |
| Secrets | Render environment / secret store | US-East | Not in source control |
| Logs | Render log stream + Grafana Cloud (Loki) | US-East | 30-day retention; PII scrubbed from logs |

No data leaves the US. No data is sent to third-party AI / analytics services.

## Authentication & access control

- Coach/AD accounts: email + password (bcrypt hashed, cost factor 12)
- JWT tokens, 15-minute access token + 7-day refresh, signed with rotating secret
- Third-party OAuth tokens (e.g. Blackbaud SKY access + refresh tokens) are encrypted at the application layer with AES-256-GCM (key derived from `JWT_SECRET` via HKDF) before being written to Postgres -- defense in depth on top of database-level at-rest encryption
- Role-based access: `SUPER_ADMIN`, `ADMIN`, `COACH`, `COMMUNITY` -- enforced on every API route
- Multi-tenant isolation: every tenant-scoped table carries `school_id`; queries are filtered server-side; no cross-school data exposure possible
- No public read endpoints expose roster data; calendar feeds (ICS) include event titles + times only, no student names

## Data lifecycle

- **Creation:** Only by authenticated TCA users or via authorized API sync (Blackbaud)
- **Modification:** Only by authenticated TCA users; every change audit-logged
- **Retention:** Indefinite while TCA is an active customer; archived after season close
- **Deletion:** TCA can request full data export and/or deletion at any time. Standard turnaround: 30 days. Backups age out within 30 days of deletion.
- **Off-boarding:** If TCA terminates the relationship, all production data is exported in standard formats (CSV/JSON), then deleted within 60 days.

## Security practices

- Dependencies scanned weekly for CVEs
- Code review required before merging to `main`
- Production deploys via CI -- no manual SSH to production servers
- Secrets rotated on staff turnover or at minimum annually
- HTTPS enforced everywhere (HSTS); no HTTP fallback
- CSRF protection on all state-changing routes
- SQL injection prevented via ORM-only data access (Prisma)

## Compliance notes

- AthleticOS is not currently SOC 2 / FERPA-certified -- we're a small project. We follow the practices above and are prepared to walk through any specific FERPA / state requirement TCA flags.
- We will sign a data processing agreement (DPA) if TCA requires one. Draft available on request.
- No data shared with any third party except as required to provide the service (Render hosting, Twilio for SMS notifications, SMTP provider for email).
